# План повышения качества ИИ-конвейера

Документ задаёт последовательность небольших изменений, которые делают поиск
поставщиков воспроизводимым, измеримым и безопасным. Новые агенты добавляются
только тогда, когда отдельная роль уменьшает измеряемый класс ошибок. Модель
остаётся интерпретатором недоверенных данных, а окончательное решение
контролируют детерминированные валидаторы, policy gate и человек.

## Текущий статус

- [x] Этап 1: Execution Manifest, `correlation_id` и версии контрактов.
- [x] Этап 2: раздельные raw, parsed, validation и policy-артефакты.
- [ ] Этап 3: replay без изменения исходного запуска.
- [ ] Этап 4: версионированный supplier eval.
- [ ] Этап 5: retry policy, бюджеты и стабильные reason codes.
- [ ] Этап 6: OpenTelemetry без утечки коммерческих данных.
- [ ] Этап 7: shadow/canary и калибровка качества.

Статус меняется только после выполнения проверок соответствующего этапа.

## Цели

1. Воспроизвести решение по сохранённым входам без повторного доступа к сайту.
2. Определить точный этап и причину каждого ошибочного допуска или отклонения.
3. Сравнивать модели, промпты и правила на одном версионированном наборе.
4. Уменьшать ложный допуск другого вещества и неподтверждённого производителя.
5. Ограничивать время, число вызовов и стоимость каждого запуска.
6. Наблюдать конвейер без вывода коммерческих данных в технические журналы.

## Неподвижные инварианты

- Отсутствующее доказательство не превращается в положительный факт.
- Исходный документ сохраняется отдельно от машинной интерпретации.
- Производитель, дистрибьютор и неподтверждённый кандидат не смешиваются.
- LLM-уверенность не считается вероятностью истинности без калибровки.
- Внешний текст не может разрешить инструмент или внешнее действие.
- Финальный выбор поставщика и отправка остаются за человеком.

## Этап 1. Execution Manifest и версии контрактов

**Изменения**

- UUID `correlation_id` на весь запуск поиска;
- `graph_version` у запуска;
- `contract_version` у каждого этапа;
- показ идентификатора и версий в API и технической трассировке.

**Проверка**

- два запуска получают разные валидные UUID;
- перезапуск не переиспользует идентификатор старого исполнения;
- все этапы получают известную версию контракта;
- API list/detail/job возвращают одинаковый `correlation_id`;
- PostgreSQL up/down-миграции имеют симметричный состав;
- старые строки получают детерминированные legacy-идентификаторы.

**Критерий готовности**

По одному идентификатору можно связать запуск, его этапы и последующую
телеметрию; неизвестная версия контракта не создаётся молча.

## Этап 2. Разделение артефактов и решений

Для LLM-этапа отдельно сохраняются сырой ответ модели, parsed output,
результат детерминированных валидаторов, итоговый policy decision, стабильные
reason codes и хеши входных артефактов.

**Проверка**

- malformed JSON не выглядит как бизнес-отклонение;
- неверная цитата остаётся в rejected claims, но не становится доказательством;
- повторный validator pass не изменяет исходный ответ модели;
- API и UI показывают слой, на котором возникла ошибка.

## Этап 3. Replay

1. `validator` — старый ответ модели, новые валидаторы и policy.
2. `model` — сохранённые документы, новая модель или промпт.
3. `live` — новая загрузка источников с отдельными снимками.

**Проверка**

- validator replay не вызывает сеть и LLM;
- model replay не вызывает поисковик и загрузку страниц;
- исходный запуск остаётся неизменяемым;
- replay создаёт новый correlation ID и ссылку на родительский запуск;
- повторная регистрация кандидата остаётся идемпотентной.

## Этап 4. Версионированный supplier eval

Набор включает точное вещество и производителя, дистрибьютора, другой CAS,
соль/смесь/аналог, неподходящий грейд, противоречащие документы, китайские,
индийские и русские источники, копии страниц, malformed/no-LLM и prompt
injection.

Метрики: `substance_false_accept_rate`, `manufacturer_false_accept_rate`,
`citation_precision`, `shortlist_precision`, `retrieval_recall_at_n`,
`abstention_rate`, `auditor_overturn_rate`, p50/p95 latency и число вызовов.

**Проверка**

- один dataset version даёт сравнимый отчёт для двух конфигураций;
- каждый пример содержит ожидаемые claims и policy decision;
- safety-набор блокирует релиз при новом ложном допуске;
- конфигурация прогоняется повторно для оценки run-to-run variance.

## Этап 5. Retry и budgets

Добавляются лимиты страниц, запросов, LLM-вызовов, токенов и общего времени,
повтор только временных ошибок, максимум один schema-repair, `attempt_number`,
`retry_reason`, `stop_reason` и идемпотентный ключ внешних операций.

**Проверка**

- логическая ошибка не вызывает повтор;
- timeout соблюдает лимит попыток;
- исчерпание бюджета возвращает безопасный частичный результат;
- один idempotency key не создаёт две внешние операции.

## Этап 6. OpenTelemetry

Один trace связывается с correlation ID; spans создаются для workflow, LLM,
поиска, загрузки, валидаторов и policy gate. Содержимое документов и промптов
не экспортируется по умолчанию.

**Проверка**

- дочерние spans имеют один trace ID;
- ошибки содержат безопасный reason code;
- telemetry не содержит страницы, email и секреты;
- выключенная телеметрия не меняет бизнес-поведение.

## Этап 7. Калибровка и безопасное внедрение

Разделяются `model_confidence`, `evidence_score`, `calibrated_probability` и
`decision`; экспертные решения становятся размеченной обратной связью. Новые
конфигурации проходят shadow-сравнение, затем canary с rollback по
safety-метрикам.

**Проверка**

- калибровка строится только на adjudicated labels;
- shadow-результат не влияет на пользователя и внешние действия;
- ухудшение false-accept метрик блокирует продвижение;
- UI не называет некалиброванный балл вероятностью.

## Общий regression gate

Каждая вертикаль завершается:

1. узкими unit/integration тестами изменённого правила;
2. полным backend `pytest`;
3. production-сборкой frontend;
4. `docker compose config`;
5. `git diff --check`;
6. обновлением API-типов и эксплуатационной документации.
