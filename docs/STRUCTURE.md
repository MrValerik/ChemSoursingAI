# Структура репозитория

Раскладка следует блочной архитектуре из ТЗ. Ниже показано фактическое состояние
репозитория; целевые компоненты, которые ещё не реализованы, отмечены отдельно.

```
ChemSoursingAI/
├── backend/                  # L1–L3, L7: API, прикладные сервисы, оркестрация, данные
│   └── app/
│       ├── api/              # L1: HTTP-эндпоинты (BFF/API Gateway)
│       ├── core/             # конфиг, настройки, общие утилиты
│       ├── models/           # L7: ORM-модели (сущности из ТЗ)
│       ├── schemas/          # Pydantic-схемы запросов/ответов и JSON-схема котировки
│       ├── services/         # L2: бизнес-логика (RFQ, котировки, эскалации, шаблоны)
│       ├── connectors/       # L5: адаптеры внешних интеграций (PubChem, Email, web)
│       ├── extraction/       # L3–L4: structured output, правила, валидаторы, LLM
│       └── eval/             # версионированные offline-eval датасеты и раннеры
│   ├── tests/                # pytest: API, бизнес-правила и интеграционные контракты
│   └── scripts/              # локальный сквозной demo-поток
├── frontend/                 # L1: SPA — рабочее место специалиста (React + TS)
├── whatsapp-web/             # изолированный неофициальный Web gateway (Node/Chromium)
├── ml/                       # резерв под отдельные ИИ-артефакты и eval
├── data/
│   └── synthetic/            # синтетический корпус писем для отладки без боевых доступов
├── tools/
│   └── telegram-agent/       # локальный Windows-мост Telegram -> официальный Codex SDK
├── .agents/skills/           # общие репозиторные workflows Codex для всей команды
├── .github/workflows/        # обязательные CI-проверки GitHub Actions
├── deploy/                   # systemd, миграции и автоматическое обновление ВМ
├── docs/                     # продуктовая, архитектурная и эксплуатационная документация
├── docker-compose.yml        # Postgres, Redis, backend, workers, WhatsApp gateway и frontend
└── AGENTS.md                 # постоянные цели и правила работы Codex
```

Корневой `AGENTS.md`, `.agents/skills`, `.github/workflows` и `deploy/`
коммитятся вместе с кодом. Это обеспечивает одинаковые правила и команды Codex
у обоих разработчиков. Локальными остаются только секреты, SSH-ключи и профили
внешних CLI.

`tools/telegram-agent` — вспомогательный контур разработки, а не часть
production-приложения ChemSource AI. Его `.env`, виртуальное окружение, временные
вложения и состояние сессий остаются только на компьютере разработчика.

Общие правила интерфейса описаны в `docs/DESIGN_SYSTEM.md`. Реализация базовых
полей и монохромных иконок находится в `frontend/src/components/ui.tsx`, а
общие визуальные токены — в `frontend/src/ui.css`.

## Принципы

- **Слабая связанность.** Внешние интеграции скрыты за слоем `connectors` с единым интерфейсом и fallback — смена провайдера не затрагивает ядро.
- **LLM через OpenAI-совместимый API.** Смена модели (llama-server → vLLM) — изменение конфигурации, а не кода.
- **Конфигурация извне.** Все параметры — через переменные окружения (см. `.env.example`).
- **Проверяемость.** Выводы о веществе и поставщике сопровождаются источником,
  уверенностью и причиной статуса.
- **Независимый аудит поставщиков.** После предварительной квалификации
  `backend/app/services/supplier_verification.py` применяет veto-only gate к
  выводу отдельного агента `supplier_verifier`: он может подтвердить только
  уже доказанный результат, а конфликт или недоступность отправляют кандидата
  на ручную проверку.
- **Версионированное исполнение.** Каждый поиск имеет `correlation_id` и версию
  графа, а каждый этап — явную версию typed-контракта. План развития replay,
  eval и наблюдаемости зафиксирован в `docs/AI_QUALITY_ROADMAP.md`.
- **Разделение артефактов.** Сырой ответ модели, typed parsing,
  детерминированная валидация и итоговый policy decision сохраняются
  раздельно; итоговый JSON интерфейса не подменяет эти слои аудита.
- **Ролевые профили общения.** Профиль и его версия хранятся отдельно от
  промпта; для каждого входящего события аудит фиксирует фактический профиль,
  версию промпта, policy-решение, токены, стоимость и причину остановки.
- **Изолированный validator replay.** Повторная проверка сохранённого ответа
  аудитора создаёт дочерний запуск с новым `correlation_id` и не вызывает сеть,
  LLM или повторную регистрацию поставщика; исходная трасса не изменяется.
- **Версионированный supplier eval.** `backend/app/eval` хранит ловушки
  decision-слоя (`supplier_decision_eval.v1.json`), eval фасовки и
  воспроизводимый набор сложных поисковых снимков
  (`supplier_model_eval.v1.json`). Сравнительный раннер разделяет retrieval,
  extraction и policy, считает ложные допуски вещества/производителя, latency,
  токены, стоимость и variance. Живые вызовы моделей выполняются только
  отдельной явной командой; safety-регрессия блокирует продвижение независимо
  от цены модели.
- **Безопасный внешний контур.** Отправка по умолчанию выключена или создаёт
  черновик; интеграции включаются явно.

## Целевые компоненты

Следующие элементы предусмотрены архитектурой, но не должны считаться
реализованными только по наличию каталога или записи в ТЗ:

- отдельные воркеры и промышленная очередь задач;
- объектное хранилище и антивирусная обработка вложений;
- OCR/vision-конвейер;
- pgvector/RAG и golden-датасет реальных писем;
- входящий webhook официального WhatsApp Cloud API, коннекторы WeChat и Echemi;
- Kubernetes и полный стек метрик/трейсов.
