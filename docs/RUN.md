# Запуск ChemSource AI

## Готовый демонстрационный сценарий

Переменная `DEMO_WORKSPACE_ENABLED=true` создаёт при старте один синтетический
запрос по ацетилсалициловой кислоте с завершённым поиском, тремя оценёнными
поставщиками, сохранёнными страницами и цитатами, готовыми email-диалогами и
тремя котировками для сравнительной таблицы. Повторные старты не дублируют
данные. В интерфейсе сценарий отображается без специального префикса; его
технический признак хранится отдельно в данных запроса. Контакты и источники
используют зарезервированный домен `.example`, реальная отправка не выполняется.

В Docker Compose сценарий включён по умолчанию для демонстрационного стенда.
Для рабочего контура задайте `DEMO_WORKSPACE_ENABLED=false` до первого запуска.

Три способа: быстрый локальный (SQLite, без Docker), полный стек приложения
через Docker Compose (Postgres + Redis) и прогон тестов/демо. LLM подключается
отдельным профилем: текущий production использует Yandex AI Studio.

## 1. Быстрый локальный запуск (SQLite, без Docker)

Подходит для разработки и демо ядра без инфраструктуры.

```bash
cd backend
pip install -r requirements.txt

# Вариант А: демонстрация сквозного потока (печатает сводную таблицу)
python scripts/demo.py

# Вариант Б: поднять API на SQLite
#   (Windows PowerShell)
$env:DATABASE_URL="sqlite:///./dev.db"; uvicorn app.main:app --reload
#   (Linux/macOS)
DATABASE_URL=sqlite:///./dev.db uvicorn app.main:app --reload
```

API: <http://localhost:8000> · Swagger UI: <http://localhost:8000/docs>

## 2. Полный стек (Docker Compose: Postgres + Redis + бэкенд)

Стек приложения в управляемом контуре заказчика. Требуется установленный Docker.

```bash
# из корня репозитория
cp .env.example .env
# Обязательно замените POSTGRES_PASSWORD и AUTH_SECRET_KEY в .env.
docker compose up --build
```

Поднимутся шесть сервисов: `db` (Postgres + pgvector), `redis`, `backend`,
`search-worker`, `renderer` и `frontend` (nginx + собранное React-приложение).
`search-worker` выполняет сохранённые в PostgreSQL задания поиска с общей
настраиваемой квотой параллельных LLM-вызовов.

`renderer` открывает браузером те страницы, которые обычным запросом не
читаются: часть сайтов присылает не страницу, а программу — ответ 200 длиной
меньше килобайта из одного упакованного скрипта, — и содержимое появляется
только после его исполнения. Служба отдаёт текст, а не снимок экрана, поэтому
дословные цитаты проверяются как обычно. Вынесена отдельно, потому что
исполняет чужой JavaScript с сайтов поставщиков. Путь необязательный: пустой
`PAGE_RENDER_URL` выключает его, и поиск работает как раньше. Запрет
`robots.txt` проверяется до обращения к службе и браузером не обходится.
Образ тянет за собой Chromium и весит около двух гигабайт.
Бэкенд дождётся готовности БД, а frontend — готовности backend; таблицы
создадутся при старте API.

Остановить: `docker compose down` (данные БД сохраняются в томе `pgdata`;
для полной очистки — `docker compose down -v`).

### Изолированный локальный стенд LLM (не текущий production)

Этот вариант сохранён для разработки, offline-измерений и изолированных
стендов. Он не описывает текущий production и не является целевым privacy
gateway. Большой GGUF-файл хранится вне Docker, а `llama-server` работает как
отдельная systemd-служба. Исторически стенд использовал Qwen3.5-27B Q4_K_M с
частичным переносом слоёв на Tesla T4. Пример службы находится в
`deploy/qwen.service.example`:

```bash
# Выполняется один раз после клонирования проекта на ВМ:
sudo cp deploy/qwen.service.example /etc/systemd/system/qwen.service

sudo systemctl daemon-reload
sudo systemctl enable qwen.service
sudo systemctl restart qwen.service
curl http://127.0.0.1:8000/v1/models

# Из корня проекта:
cp .env.example .env
docker compose up --build -d
curl http://127.0.0.1/api/health/llm
```

`docker-compose.yml` направляет запросы backend-контейнера к хосту через
`host.docker.internal:8000`. Порт 8000 нужен только внутри ВМ: **не открывайте его
во входящих правилах Yandex Cloud**. Для сайта откройте TCP 80 (после подключения
HTTPS также 443). SSH-порт 22 ограничьте вашим IP.

У всех контейнеров задано `restart: unless-stopped`: после перезапуска ВМ Docker
поднимет сайт и базу автоматически, а systemd отдельно запустит Qwen. При штатной
остановке ВМ данные PostgreSQL сохраняются в томе `pgdata`.

Без LLM конвейер извлечения работает на правилах (fallback) — система остаётся
работоспособной.

### Подключение облачной LLM через OpenAI-совместимый API

Backend не зависит от конкретного облачного провайдера. Для Yandex AI Studio
задайте в локальном `.env` (не коммитьте настоящий ключ):

```env
LLM_BASE_URL=https://llm.api.cloud.yandex.net/v1
LLM_MODEL=gpt://<folder_ID>/qwen3.6-35b-a3b/latest
LLM_API_KEY=<API_key>
LLM_AUTH_SCHEME=api-key
LLM_PROJECT_ID=<folder_ID>
LLM_THINKING_CONTROL=chat_template_kwargs
LLM_PARALLEL_SLOTS=8
```

`LLM_AUTH_SCHEME=api-key` формирует `Authorization: Api-Key ...`, а
`LLM_PROJECT_ID` — заголовок `OpenAI-Project`. Локальная конфигурация
использует `bearer` и пустой project.

`LLM_THINKING_CONTROL` обязателен для рассуждающих моделей. Замер на
Qwen3.6 в AI Studio без него: 2205 символов рассуждения, 700 выходных
токенов из 700, `content` пустой, `finish_reason: length`. Работают
`chat_template_kwargs` и `reasoning_effort`; маркер `/no_think` в тексте
запроса — нет. Значение `none` оставлено для моделей без такого режима.

`LLM_PARALLEL_SLOTS` в облаке нужно поднимать: он ограничивает число
одновременных вызовов и введён под очередь одного llama-server. У облака
такой очереди нет, и единица здесь просто отменяет параллельность.

Текущий production работает на непрерываемой CPU-ВМ `chemsource-prod`
(`epdktu42uskhkt9iqghu`) и использует Yandex AI Studio. Локальный
`qwen.service` для этого стенда не устанавливается; deployment считает его
опциональным и проверяет модель через `/api/health/llm`.

### Целевая схема: локальная Qwen-8B перед облачной LLM

Утверждённая целевая архитектура добавляет в контур заказчика отдельный privacy
gateway на Qwen-8B. Он должен классифицировать, удалять и псевдонимизировать
чувствительные сведения, после чего детерминированный validator либо разрешает
отправку очищенного запроса в Yandex AI Studio, либо блокирует облачный вызов и
создаёт ручную эскалацию.

На 29.08.2026 этот gateway ещё не реализован. Основной `LLM_*`-профиль и
`COMMUNICATION_TEST_LLM_*` обращаются к облаку без автоматической локальной
очистки, поэтому production нельзя считать соответствующим целевой схеме до
реализации и прохождения security-eval.

Будущая реализация обязана быть fail-closed: недоступность Qwen-8B, malformed
structured output, неизвестная политика, найденный после очистки секрет или
потеря обязательного факта запрещают облачный вызов. Прямой fallback исходного
текста в облако запрещён. Не добавляйте предполагаемые переменные окружения в
боевой `.env`, пока их контракт не реализован в backend и Compose.

Полный поток данных, таксономия, audit и критерии приёмки описаны в
[`docs/LLM_PRIVACY_GATEWAY.md`](LLM_PRIVACY_GATEWAY.md).

### Модель только для общения и его документов

На production общение переведено на DeepSeek V4 Flash в том же Yandex AI Studio.
Основной `LLM_MODEL` (Qwen) для поиска, квалификации поставщиков и документов
вне переписки не меняется. Для включения задайте в `.env`:

```env
COMMUNICATION_LLM_MODEL=gpt://<folder_ID>/deepseek-v4-flash/latest
COMMUNICATION_LLM_THINKING_CONTROL=reasoning_effort
```

Общий профиль общения наследует адрес, ключ, авторизацию, каталог и лимиты
основного `LLM_*`. Для Flash V4 `reasoning_effort` отправляет `none`, чтобы
ответ не расходовал лимит на скрытые рассуждения. Модель применяется к Email,
WhatsApp, тестовым диалогам, классификации ответов, извлечению котировок из
переписки и проверке её вложений (включая ручную повторную проверку).
OCR/извлечение текста остаются локальными; независимые проверки CAS, цитат,
полноты и опасных условий не меняются. Исходные письма не переписываются,
старые результаты автоматически не пересчитываются.

Явный `COMMUNICATION_LLM_MODEL` имеет приоритет над прежним
`COMMUNICATION_TEST_LLM_*`, поэтому песочница и email-worker используют ту же
модель, что и блок общения. Пустое значение возвращает прежнюю маршрутизацию:
обычное общение — основной LLM, песочница — выделенный профиль ниже.
Обе новые настройки передаются в backend и email-worker через Compose;
после изменения `.env` выполните штатное обновление сервера.

Это не privacy gateway: текст переписки/вложений по-прежнему обрабатывается
в Yandex AI Studio без автоматической локальной очистки. Для проверки выбранной
модели смотрите `model` результата документа/тестового диалога; `/health/llm`
проверяет основной профиль, а не отдельную генерацию Flash V4.

#### Контроль качества продолжения диалога

Правила `reply_quality.v2` применяются к общим черновикам блока общения (Email,
WhatsApp и тестовый диалог). Модель сначала отвечает на последний вопрос,
учитывает историю поставщика и запрашивает приоритетные пробелы, не повторяя
весь RFQ. Для неизвестной тары или реквизитов покупателя сначала требуется
внутреннее уточнение. Размер упаковки не заменяет MOQ, а запрошенный грейд —
подтверждение поставщика. Полностью полученное предложение передаётся на
внутреннюю проверку без дополнительных выдуманных требований.

Детерминированные проверки отклоняют типовые подтверждения заказа/оплаты,
самостоятельный выбор тары, повторные вопросы о явно закрытых условиях и
слишком длинные реплики. Одна исправляющая генерация разрешена; повторная
ошибка оставляет диалог в `llm_error` и запрещает отправку этого черновика.
Это набор ограниченных проверок, а не доказательство безошибочности модели.
Policy-gate и решение человека о закупке сохраняются.

Проверка документов принимает стандартные метки партии `Batch No.`, `BatchNo`
и `Lot No.` без обязательного двоеточия, но не допускает несовпадающий номер.
`Issue Date` и `Analysis Date` не считаются датой производства. Цитаты должны
быть непрерывными дословными фрагментами, без многоточий вместо пропусков.
Название стандарта EP/USP/BP должно присутствовать в цитате, а не выводиться
из набора испытаний или общего слова `STANDARD`.
Упоминание CoA внутри TDS не меняет тип документа; TDS без партии не подтверждает
качество конкретной партии. Старые результаты автоматически не переписываются.

Набор `backend/app/eval/datasets/communication_quality.v1.json` содержит только
синтетические данные. Обычные pytest не вызывают LLM. Для согласованной платной
проверки настроенной модели из каталога `backend`:

```powershell
..\.venv\Scripts\python.exe -m app.eval.communication_quality --live --repeat 2
```

Прогон печатает JSONL с моделью, сценарием, черновиками, временем и замечаниями;
не отправляет сообщения и не сохраняет бизнес-данные. Технические LLM-операции
используют штатный механизм ограничения конкурентных запросов. Регулярные
выражения оценивают конкретные ошибки, поэтому результаты дополнительно
проверяются по смыслу. Реальную переписку и результаты её разбора в Git не
сохранять. Проверка реальных данных требует отдельного согласования.

Для отдельного администраторского раздела «Тестирование общения» без общего
`COMMUNICATION_LLM_MODEL` используется
облачный профиль. Он позволяет оставить поиск на одной модели, а живость и
качество диалога проверять на более мощной модели независимо:

```env
COMMUNICATION_TEST_LLM_BASE_URL=https://llm.api.cloud.yandex.net/v1
COMMUNICATION_TEST_LLM_MODEL=gpt://<folder_ID>/qwen3.6-35b-a3b/latest
COMMUNICATION_TEST_LLM_API_KEY=<API_key>
COMMUNICATION_TEST_LLM_AUTH_SCHEME=api-key
COMMUNICATION_TEST_LLM_PROJECT_ID=<folder_ID>
COMMUNICATION_TEST_LLM_THINKING_CONTROL=chat_template_kwargs
COMMUNICATION_TEST_LLM_TIMEOUT_S=600
```

Если весь выделенный профиль пуст, локальная разработка безопасно использует
основной `LLM_*`-профиль. Частично заполненный профиль считается ошибкой
конфигурации и не смешивается с реквизитами другого провайдера.

Список доступных моделей каталога:

```bash
curl -s https://llm.api.cloud.yandex.net/v1/models \
  -H "Authorization: Api-Key $LLM_API_KEY" \
  -H "OpenAI-Project: $LLM_PROJECT_ID"
```

Существующий structured output остаётся совместимым: Chat Completions получает
`response_format.type=json_schema`, переданную JSON Schema и `strict=true`.
Health-check использует стандартный `GET /v1/models` с теми же заголовками
авторизации. Для Yandex API-ключ должен иметь права на выполнение моделей и их
просмотр; ключ, созданный в AI Studio, выдаётся с нужными областями доступа.

## 3. Обновление локального репозитория

Из чистой ветки `main`:

```powershell
.\deploy\update-repository.cmd
```

Скрипт получает `origin/main` и применяет только безопасный fast-forward. Он не
отправляет локальные коммиты, не запускает ВМ и не обновляет production. При
незакоммиченных изменениях или расхождении веток выполнение останавливается без
изменения файлов.

В Codex тот же сценарий доступен как `$update-repository` с названием
«Обновить репозиторий».

Для вопросов о проекте и явных задач на исправление можно запустить на Windows

## 5. Тесты

```bash
cd backend
pytest
```

Безопасностный eval decision-слоя поиска поставщиков входит в pytest
(`tests/test_supplier_eval.py`) и дополнительно доступен как отдельная
команда с метриками и кодом возврата для release gate:

```bash
cd backend
python scripts/run_supplier_eval.py --version v1
```

Код `2` означает новый ложный допуск на safety-примере и блокирует релиз;
`--full-report` печатает разбор каждого примера. Датасет версионирован:
`app/eval/datasets/supplier_decision_eval.v1.json`; изменение примеров — это
новая версия файла, а не правка старой.

### Сравнительный eval моделей на сложном поиске поставщиков

`supplier_model_eval.v1` воспроизводимо передаёт двум конфигурациям одинаковые
синтетические снимки выдачи и первичных страниц. Набор покрывает редкое
вещество, широкий каталог, лабораторную фасовку для промышленного запроса,
другое соединение, аналог, китайский и индийский источники, недоступную
первичную страницу и prompt injection. Retrieval остаётся зафиксированным, так
что различия extraction и policy не смешиваются с изменением живой web-выдачи.

Стандартный `pytest` не вызывает web или LLM. Он проверяет схему dataset/report,
offline fixtures для malformed/no-LLM/prompt injection и правила promotion
gate. Живой OpenAI-совместимый прогон запускается только вручную с явным
флагом:

```powershell
Push-Location .\backend
try {
    Copy-Item `
        -LiteralPath .\scripts\supplier_model_eval_configs.example.json `
        -Destination .\scripts\supplier_model_eval_configs.local.json
    # Заполните локальный файл именами env-переменных, моделями и тарифами.
    ..\.venv\Scripts\python.exe .\scripts\run_supplier_model_eval.py `
        --allow-live-llm `
        --config .\scripts\supplier_model_eval_configs.local.json `
        --baseline current `
        --candidate alternative `
        --repeat 3 `
        --output .\supplier-model-report.json
} finally {
    Pop-Location
}
```

Локальный файл конфигураций и отчёт не следует коммитить: они могут раскрыть
внутренние адреса и коммерческие тарифы. API-ключи задаются только через имена
переменных окружения (`api_key_env`), а в отчёт не попадают. Для каждой
конфигурации отчёт содержит модель, host OpenAI-совместимого endpoint,
`prompt_version`, `manufacturer_false_accept_rate`,
`substance_false_accept_rate`, `citation_precision`, `shortlist_precision`,
`retrieval_recall_at_n`, latency, prompt/completion tokens, приблизительную
стоимость в USD и run-to-run variance.

Код возврата `2` означает safety-регрессию и безусловно запрещает продвижение
модели, даже если она быстрее или дешевле. Код `1` означает нарушение
остального quality gate. Пороговые значения версионируются вместе с dataset;
новый состав примеров выпускается новым файлом, старый не переписывается.

### Нагрузочный краш-тест поиска поставщиков

Сколько веществ можно искать одновременно — вопрос трёх независимых пределов:
API постановки в очередь, числа воркеров и числа слотов локальной модели.
Автономный тест проверяет их на заглушке модели, без GPU и сети:

```bash
cd backend
pytest tests/test_search_load.py -q -s
```

Флаг `-s` показывает измерения: burst постановки в очередь, пик параллельных
обращений к модели, лестницу «воркеры → пропускная способность» и поведение
при перегрузке.

Реальные цифры конкретного стенда снимает отдельный скрипт. Он обращается к
внешним системам, поэтому запускается вручную и только с `--yes`:

```bash
cd backend
python scripts/search_load_test.py --mode llm --yes --profile both --ladder 1,2,4
```

Режим `--mode llm` нагружает только `LLM_BASE_URL` и находит, сколько
одновременных генераций держит llama-server. Профиль обязателен для
интерпретации: `short` — служебный вызов на 400 токенов, `search` — реальный
запрос квалификации на ~9000 токенов входа и structured output. Конфигурация
с делённым контекстом проходит `short` с лучшими цифрами в таблице и падает на
`search` целиком, поэтому мерить надо профилем `search`. Телеметрию сервера
скрипт снимает, если llama-server запущен с `--metrics` **и** `--slots`: это
два разных флага, одного `--metrics` для `/slots` недостаточно.

Замер на стенде (Tesla T4 16 ГБ, Qwen3.5-27B Q4_K_M, `-ngl 40`, промпт 8112
токенов — реальный запрос квалификации, по 6 запросов на ступень):

| Конфигурация | Параллельность | p50 | Запросов/час |
| --- | --- | --- | --- |
| `--parallel 1 --ctx-size 12288` | 1 | 58 с | 55.8 |
| `--parallel 1 --ctx-size 12288` | 2 | 115 с | 62.4 |
| `--parallel 2 --ctx-size 24576` | 2 | 86 с | 84.1 |
| `--parallel 2 --ctx-size 24576` | 4 | 170 с | 84.7 |

Второй слот занимает около 916 МиБ VRAM и на T4 помещается: после загрузки
модели свободно 2602 МиБ против 3518 МиБ при одном слоте. Пропускная
способность выходит на полку при параллельности, равной числу слотов:
запросы сверх этого не ускоряют работу, а только удваивают задержку.

### Квантование под размер карты

`Q4_K_M` весит 16.75 ГиБ и в 15 ГиБ T4 не помещается — отсюда `-ngl 40` и
счёт части каждого токена на CPU. Именно эта выгрузка, а не размер модели,
определяет пропускную способность. `Q3_K_S` (12.98 ГиБ) помещается целиком
вместе с двумя слотами, если квантовать KV-кэш:

```
--model .../Qwen_Qwen3.5-27B-Q3_K_S.gguf --n-gpu-layers 99 \
  --ctx-size 24576 --parallel 2 --cache-type-k q8_0 --cache-type-v q8_0 \
  --flash-attn on
```

Замер на том же профиле `search`, по 6–8 запросов на ступень:

| Конфигурация | Оптимум | p50 | prefill | Запросов/час |
| --- | --- | --- | --- | --- |
| Q4_K_M, `-ngl 40`, 2 слота | параллельность 2 | 85.6 с | 190 т/с | 84.1 |
| Q3_K_S, целиком на GPU, 2 слота, KV q8 | параллельность 4 | 37.7 с | 850 т/с | **377.0** |

Полка у Q3_K_S — на параллельности 4–6 (377 и 389 запросов/час), при 8 растёт
только задержка. Загрузка модели занимает 20 с против 290 с у частично
выгруженной Q4, VRAM 14430 МиБ из 15360.

Это ускорение получено сменой квантования, а не модели: параметров столько же.
Качество решений при более грубом квантовании **не проверено** — прежде чем
переносить конфигурацию в прод, нужно сравнение ответов с действующей Q4_K_M
на одинаковых страницах.

CAS обязателен только для режима идентификации по CAS. Для смеси, рецептуры,
промышленного продукта или поиска аналога задача запускается без обращения к
PubChem и использует название, подтверждённые синонимы, спецификацию и назначение.
В режиме аналога в поисковые запросы обязательно включается эталонный торговый
продукт и признаки `equivalent / alternative / substitute` (для Китая также
китайские формулировки). В форме запроса для аналога отдельно заполняются
критерии эквивалентности: состав/INCI, активное содержание и измеримые свойства.
Они сохраняются как спецификация и дают отдельную безбрендовую ветку поиска.
Если в исходном названии явно перечислены разные формы (`free base or sulfate`),
fallback ищет их отдельными запросами, не склеивая пояснение закупщика в
несуществующее товарное имя. Неуказанную соль, катион или грейд система не
придумывает. Найденная замена не считается точным эквивалентом и не попадает в
короткий список автоматически: требуется ручное сравнение состава, ключевых
свойств, грейда и применения.

Для локальной модели 27B оставляйте `LLM_TIMEOUT_S=600`: квалификация пакета
первичных страниц на одной GPU может занимать больше пяти минут. Для надёжного
строгого JSON этап квалификации обрабатывает кандидатов внутренними пакетами по
две компании и объединяет их в один пользовательский результат. Затем отдельный
этап трассировки `supplier_verifier` независимо сверяет первичную страницу и
проверенные утверждения, не получая итоговых меток первого агента. Он работает
как veto-only gate: без подтверждения точного вещества и роли производителя
кандидат не включается в короткий список, а при недоступности модели остаётся
доступным для ручной проверки. Поиск заранее
сохраняет резерв объёмом до трёх целевых списков (не более 60 уникальных
доменов). Недоступная первичная страница не
передаётся ИИ-агенту и автоматически заменяется следующим результатом; при
исчерпании резерва запуск получает статус ошибки, а не ложный статус успешного
завершения. Проверенные результаты автоматически связываются с запросом в
реестре поставщиков как кандидаты.

Каждый запуск поиска получает UUID `correlation_id` и `graph_version`; каждый
этап трассировки содержит `contract_version`. Эти поля возвращаются API
поисковых запусков и используются для сопоставления логов, будущих
OpenTelemetry spans и воспроизводимых replay-запусков.

Для LLM-этапов техническая трассировка отдельно возвращает
`raw_output_payload`, `parsed_output_payload`, `validation_output_payload` и
`policy_output_payload`. Совместимый `output_payload` пока сохраняется для
существующего интерфейса, но не используется как единственный источник аудита.

Размер контекста модели задаётся `--ctx-size` у `qwen.service` и дублируется
для backend в `LLM_CONTEXT_TOKENS`. Backend заранее ужимает объём первичных
страниц под этот бюджет, поэтому запрос не может превысить контекст. Если
сервер всё же отвергает запрос по длине, ошибка показывается как переполнение
контекста с числом токенов, а не как «модель недоступна», и не повторяется:
повтор не изменит результат.

Каждый этап дополнительно ведёт человекочитаемый журнал действий `events`
(время, тип, сообщение): какой запрос выполняется, какая страница открыта,
сколько оценок вернула модель, почему этап остановился. События коммитятся по
ходу выполнения, поэтому интерфейс показывает журнал бегущего этапа почти в
реальном времени — раскройте шаг конвейера на вкладке «Поиск и проверка».

`validator` replay создаёт новый `correlation_id`, сохраняет
`parent_search_run_id` и повторно применяет текущий typed-контракт и veto gate
`supplier_verifier` к сохранённому сырому ответу. Replay не выполняет поиск,
загрузку страниц, вызов LLM и повторную регистрацию поставщика.

Загрузка первичных страниц выполняется с браузерными заголовками и по HTTP/2: запрос только с `User-Agent` отсекался защитой сайтов и давал 403 (проверено на `store.usp.org`: 403 против 200). Таймауты раздельные (соединение 5 с, чтение 25 с), временная сетевая ошибка повторяется один раз, а логический отказ сервера — нет. Слишком большая страница не отбрасывается, а обрезается: для оценки поставщика достаточно начала документа. Перед загрузкой соблюдается `robots.txt` домена и пауза между запросами к одному сайту; недоступный `robots.txt` не считается запретом.

Домены дистрибьюторов реактивов, продавцов фармакопейных стандартов, справочников и маркетплейсов (`NON_MANUFACTURER_DOMAINS` в `app/services/supplier_sources.py`) исключаются из выдачи до этапа загрузки: их страницы всё равно отбраковываются квалификацией как посредники, а бюджет и место в короткой выдаче они тратят.

Начиная с графа `supplier-search.v2`, квалификация отдельно сопоставляет
требуемый объём RFQ с фасовками,
диапазоном заказа и MOQ, найденными только на сохранённой первичной странице.
Масса приводится к граммам, объём — к миллилитрам; пересчёт между ними без
плотности запрещён. Поддерживаются распространённые английские, русские и
китайские обозначения, включая `GM`, `lb`, `кг`, `公斤`, `吨` и `升`.
Подтверждённая несовместимость блокирует короткий список,
а отсутствие данных даёт `unknown`, уменьшает доказательный балл на 5 и
показывает недостающее поле. Для MVP промышленный масштаб фасовки/MOQ начинается
с 20 kg или 20 L; пороги настраиваются через
`SUPPLIER_INDUSTRIAL_PACKAGE_MIN_MASS_KG` и
`SUPPLIER_INDUSTRIAL_PACKAGE_MIN_VOLUME_L`. Поисковый сниппет в это решение не
входит. Интерфейс показывает потребность, найденные значения, дословную цитату,
URL и причину решения.
HTML разбирается с сохранением границ таблиц, `label/select/option` и
`dt/dd`; маркер фасовки или MOQ может быть связан с последующими чистыми
строками количества в пределах короткого окна. Такая связь получает метод
`adjacent_lines` и среднюю уверенность, сохраняет исходные строки цитаты и
останавливается на цене, описании либо следующей карточке товара. При наличии CAS
количественные факты ограничиваются окрестностью искомого вещества и границами
секций наподобие `Related Products`/`Frequently Bought Together`. Удалённая
строка MOQ или диапазона принимается только когда она сама повторяет искомый CAS
либо подтверждённое название. Пары `PropertyValue` и `QuantitativeValue` из
JSON-LD также преобразуются в проверяемые строки имя/значение. Эти правила
покрывают страницы, где `Pack Size`, `500 g` и `1 kg` находятся в соседних
DOM-узлах, не превращая числа из другого товара в доказательство.
Offline-набор `supplier_volume_eval.v1` входит в pytest и публикует метрику
`laboratory_supplier_false_accept_rate`; новый ложный допуск лабораторной
фасовки является регрессией release gate.

Каждый этап поиска ограничен бюджетом: `SEARCH_MAX_QUERIES`,
`SEARCH_MAX_PAGE_FETCHES`, `SEARCH_MAX_LLM_CALLS` и `SEARCH_MAX_RUNTIME_S`.
Исчерпание бюджета не является ошибкой: этап останавливается на безопасном
частичном результате, неквалифицированные кандидаты уходят на ручную
проверку, а в выводе этапа сохраняются `stop_reason` и снимок использования
бюджета.

Структурированные LLM-вызовы повторяют только временные ошибки сети и
сервера (timeout, 5xx, 429) и не более одного раза; malformed JSON получает
не более одного schema-repair вызова. Логические ошибки не повторяются.
Журнал попыток с `attempt_number`, `kind` и `retry_reason` сохраняется в
выводе этапов квалификации и независимой проверки.

Если задача из очереди упала из-за недоступности настроенной ИИ-модели,
worker автоматически возвращает её в очередь (до трёх раз, счётчик
`llm_auto_retry_count` в параметрах задачи) и подхватывает снова, как только
модель снова отвечает; при сохранённых результатах веб-поиска повторяются
только проверка страниц, оценка и аудит. Логические ошибки в очередь не
возвращаются. Кнопка «Продолжить с проверки» делает то же самое вручную.

## Документы поставщиков: CoA, TDS и паспорт качества

Вложения входящих писем сохраняются в контуре заказчика (`ATTACHMENT_STORAGE_DIR`, том Docker) и разбираются на текст: у PDF читается текстовый слой через `pypdf`. Файл считается недоверенными данными, поэтому путь в хранилище строится из хеша содержимого, а не из имени отправителя; тип определяется по сигнатуре файла, а не по заявленному MIME; размер ограничен `ATTACHMENT_MAX_SIZE_MB`. Скан без текстового слоя честно получает статус `needs_ocr`, а не выдаётся за пустой документ. Скрытые логотипы, иконки подписи и трекинговые изображения, переданные почтовым клиентом как `inline` либо CID-связанные части, отбрасываются до сохранения. Явно приложенный PNG при этом остаётся обычным вложением.

Сохранённые Email- и тестовые вложения показываются непосредственно под
сообщением во вкладке «Общение». Кнопка скачивает оригинал через уже активную
сессию без повторного входа или отдельного подтверждения. Backend по-прежнему
проверяет право пользователя видеть соответствующий RFQ; публичные ссылки на
коммерческие документы не создаются.

Скан без текстового слоя распознаётся через Tesseract (`OCR_ENABLED`, языки `OCR_LANGUAGES`, не более `OCR_MAX_PAGES` страниц). Такой текст получает отдельный статус `ocr_extracted`: он менее надёжен, чем текстовый слой PDF, и это видно и агенту, и человеку. OCR работает на CPU, поэтому обработка скана занимает заметное время; при выключенном OCR документ честно остаётся на ручной проверке.

Проверку выполняет отдельный агент `document_verification`. Его вывод проходит детерминированный veto-gate: утверждение принимается только при дословном совпадении цитаты с сохранённым текстом, CAS сверяется кодом по контрольной сумме, а расхождение CAS в документе отклоняет паспорт независимо от уверенности модели. Основной процент «проверяемой уверенности» рассчитывает backend, а не LLM: до 45 баллов даёт совпадение идентичности, 20 — подтверждённая партия, 20 — доля дословно найденных цитат, 15 — распознанный тип и дополнительные поля; для OCR применяется понижение 15%. При заданном CAS его отсутствие нельзя заменить совпадением названия. Справочная уверенность классификатора хранится отдельно и не повышает итоговый балл. Без подтверждённых вещества и номера партии документ не принимается автоматически.

Синтетический CoA из тестового диалога проходит тот же расчёт по извлечённому тексту, CAS/названию, партии и цитатам. Маркировка `SYNTHETIC DEMONSTRATION ONLY` не считается несоответствием вещества только в явно переданном тестовом контексте; такой результат демонстрирует работу проверки, но не подтверждает подлинность документа или пригодность реальной партии. Агент не заменяет решение специалиста.

## Переменные окружения

См. `.env.example`. Ключевые: `DATABASE_URL`, `REDIS_URL`, `LLM_BASE_URL`,
`LLM_MODEL`, `LLM_AUTH_SCHEME`, `LLM_PROJECT_ID`, `LLM_THINKING_CONTROL`,
`PUBCHEM_BASE_URL`, `SUPPLIER_INDUSTRIAL_PACKAGE_MIN_MASS_KG` и
`SUPPLIER_INDUSTRIAL_PACKAGE_MIN_VOLUME_L`. Для денежного аудита общения задайте
`COMMUNICATION_LLM_INPUT_COST_PER_MILLION_USD` и
`COMMUNICATION_LLM_OUTPUT_COST_PER_MILLION_USD`; нулевые значения сохраняют
токены, но не рассчитывают стоимость. API и интерфейс показывают бюджет в рублях
по настраиваемому курсу `COMMUNICATION_COST_USD_RUB_RATE` (по умолчанию 100).
Остальные лимиты версионируются в профиле
через раздел «ИИ-промпты». Для настроек каналов, сохранённых через
интерфейс, задайте отдельный `INTEGRATION_ENCRYPTION_KEY`. Если он пуст,
используется `AUTH_SECRET_KEY`; менять применённый ключ без переноса данных
нельзя, иначе сохранённые пароли и токены перестанут расшифровываться.

## Email: безопасное включение

По умолчанию Compose использует `EMAIL_DELIVERY_MODE=demo` и не отправляет
письма наружу. Для подключения корпоративного ящика заполните в `.env`:

```env
EMAIL_DELIVERY_MODE=live
EMAIL_FROM=procurement@example.com
EMAIL_FROM_NAME=Procurement Department
# Локальный адрес владельца продукта; не добавляйте реальный адрес в Git.
FEEDBACK_EMAIL_TO=owner@example.com

SMTP_HOST=smtp.example.com
SMTP_PORT=465
SMTP_USER=procurement@example.com
SMTP_PASSWORD=change_me
SMTP_USE_SSL=true
SMTP_STARTTLS=false

IMAP_HOST=imap.example.com
IMAP_PORT=993
IMAP_USER=procurement@example.com
IMAP_PASSWORD=change_me
IMAP_USE_SSL=true
IMAP_FOLDER=INBOX

# Рекомендуется сначала draft, а после приёмки процесса — send.
AUTO_FOLLOWUP_MODE=draft
```

Эти же параметры администратор может сохранить в разделе «Настройки».
В режиме `send` внешний дозапрос строится детерминированно из сохранённого
вещества, CAS и недостающих полей; неподтверждённый LLM-черновик автоматически
не отправляется. Нестандартные вопросы, конфликт идентичности и исчерпание
лимита продолжают создавать эскалацию человеку.
Пароли SMTP/IMAP и токен WhatsApp шифруются перед записью в PostgreSQL и никогда
не возвращаются в браузер. Значения из `.env` остаются fallback для первого
запуска.

Сообщения из раздела «Обратная связь» сначала сохраняются в PostgreSQL, затем
backend отправляет внутреннее уведомление на `FEEDBACK_EMAIL_TO` через тот же
SMTP-профиль. Отправка выполняется только при включённом Email-канале и
`EMAIL_DELIVERY_MODE=live`; результат (`sent`, `disabled` или `failed`) и
`Message-ID` сохраняются для аудита. Ошибка SMTP не удаляет само обращение.

После изменения окружения пересоздайте backend:

```bash
docker compose up -d --build backend frontend
```

Проверьте статус канала в разделе «Настройки». Реальные письма отправляются
только после явного включения `live`. Синхронизация входящих запускается кнопкой
«Проверить входящие Email» на вкладке «Общение» пользователем с ролью
руководителя или администратора.

Реальные Email-диалоги из администраторского раздела «Тестирование общения»
можно продолжать автоматически отдельным worker. Он сопоставляет ответ по
`In-Reply-To`/`References` с сохранённым `Message-ID`, сначала фиксирует
входящую реплику в PostgreSQL, затем применяет шлюз безопасности. Обычный ответ
по условиям закупки передаётся выделенной `COMMUNICATION_TEST_LLM_*`-модели и
отправляется в той же почтовой цепочке. Личный, нестандартный, опасный или
неясный вопрос не получает автоответа: тестовый диалог получает статус
`escalated` и пояснение для администратора. Уникальный входящий `Message-ID` и
состояние `sending` защищают от повторной отправки после перезапуска.

Worker по умолчанию выключен. После проверки SMTP, IMAP и облачной модели
включите его только в production:

```env
COMMUNICATION_TEST_EMAIL_AUTO_REPLY_ENABLED=true
COMMUNICATION_TEST_EMAIL_POLL_INTERVAL_S=30
COMMUNICATION_TEST_EMAIL_POLL_BATCH_SIZE=20
```

Непривязанные непрочитанные письма worker не помечает прочитанными и не
обрабатывает. Настройка `AUTO_FOLLOWUP_MODE` относится к обычным RFQ и не
управляет этим явно включённым тестовым автодиалогом.

Неполный ответ поставщика сам по себе не является причиной эскалации. Короткие
реплики с ценой, MOQ, наличием, сроком или другим отдельным параметром относятся
к стандартному RFQ: нейросеть должна продолжить диалог и запросить недостающие
CAS, чистоту, валюту, Incoterm или документы. `sensitive_information`
используется только для просьбы раскрыть внутренние конфиденциальные данные
покупателя, а не для цены, добровольно названной поставщиком.

В уже начатом Email-диалоге покупатель, руководитель или администратор может
ввести ответ и явно подтвердить реальную SMTP-отправку. Backend сохраняет
попытку со статусом `sending` до обращения к SMTP, после подтверждения сохраняет
`Message-ID` и статус `sent`, а при неопределённой ошибке не повторяет действие
автоматически. Email-черновик дозапроса отправляется отдельной кнопкой в его
карточке сообщения. Если у диалога открыта эскалация, сотрудник может ответить
из её карточки: интерфейс повторно показывает канал и адресата, требует явного
подтверждения реальной отправки и закрывает эскалацию только после успешного
ответа. Стабильный ключ действия защищает повторную попытку от дублирования
сообщения, если отправка прошла, а обновление статуса эскалации временно не
удалось.

Ответ может прийти не с того локального адреса, на который отправлялся RFQ.
Для первого письма с нового адреса Email-worker сравнивает полный домен после
`@` только с адресами фактически отправленных получателей данного RFQ и всегда
выполняет вторую LLM-проверку первого письма. Автоматическая привязка требует
совпадения домена и явного упоминания названия ровно одной компании-получателя
в отображаемом имени, теме, подписи или тексте, а также уверенности не ниже 0,90
с дословной цитатой этого названия. Явное однозначное упоминание обрабатывается
сразу детерминированно; модель вызывается только для неоднозначного варианта и
не может обойти проверку цитаты. Товар, цена и соответствие содержания RFQ для
идентификации отправителя не оцениваются. Общие почтовые домены не считаются доказательством компании. Успешно проверенный адрес
становится дополнительным контактом поставщика; старые непривязанные сообщения
того же адреса проверяются один раз и объединяются с его диалогом. Метод,
уверенность и цитата сохраняются в `sender_identity` аудита. Если проверка не
пройдена, автоответ не отправляется и создаётся эскалация. Результат ручной
проверки почты отдельно показывает число связанных новых адресов.
Открытый объединённый диалог постоянно показывает, какой новый Email связан с
исходным адресом получателя.
Email-worker перед каждым тестовым IMAP-опросом отдельно повторяет эту проверку
для уже сохранённых непривязанных писем. Шаг не читает новые письма и не
отправляет ответы, поэтому временная ошибка IMAP не блокирует объединение уже
имеющейся истории. Для старого письма без policy-аудита сначала создаётся
обычный аудит активного профиля с той же проверкой бюджета; отсутствие старой
служебной записи не блокирует сверку.

Рядом с полем ответа доступна скрепка. За одно действие можно отправить до пяти
файлов PDF, PNG/JPEG/TIFF, TXT/CSV, XLS/XLSX или DOC/DOCX; размер одного файла
ограничен `ATTACHMENT_MAX_SIZE_MB`, общий размер — удвоенным лимитом. Email
получает файлы как MIME-вложения. WhatsApp Cloud API сначала загружает документ
в Media API, а внутренний WhatsApp Web gateway отправляет его как media message.
Исходящий файл сохраняется у сообщения и доступен по обычной кнопке скачивания.

Для каждого поставщика полнота условий считается по всей Email-переписке данного
RFQ, а не только по последнему письму. Цена, валюта, Incoterm, MOQ, грейд,
условия оплаты и срок могут прийти разными
ответами; сохранённые вложения CoA/TDS также участвуют в проверке. Когда полный
набор собран, вкладка «Общение» показывает статус «Данные собраны», новый
дозапрос не создаётся, а оставшийся неотправленный черновик получает статус
`cancelled` и больше не доступен для отправки.

Оригинальный текст каждого входящего письма сохраняется без изменений, но для
классификации и извлечения используется только новая реплика над цитируемой
историей. Поэтому прежние цены, условия и упоминания документов из блока
`Original Message` не выдаются за новый ответ поставщика. Если письмо содержит
несколько самостоятельных ценовых строк (например, FOB и CIP), каждая строка
сохраняется отдельной котировкой со своим базисом и объёмом. Фраза `In stock`
означает наличие, а не срок поставки; просьба покупателя прислать CoA/TDS не
подтверждает наличие этих документов. Реальное сохранённое вложение CoA/TDS
проходит проверку идентичности по веществу и CAS.

Для сверки старых котировок после обновления можно выполнить идемпотентную
команду внутри backend-контейнера. Фильтры RFQ и адреса ограничивают область
изменения:

```bash
docker compose exec -T backend python -m app.commands.reconcile_email_quotations \
  --rfq-id 30 --email sales4@example.com --verify-documents
```

Команда связывает котировки с исходными сообщениями, повторяет
детерминированное извлечение только из новых реплик, восстанавливает отдельные
ценовые варианты и проверяет ещё не проверенные документы. Письма и их
оригинальный текст не изменяются.

После сбора данных поле ответа тестового поставщика остаётся открытым. Первый
новый ответ автоматически передаёт `continue_after_complete=true`; backend
сохраняет историю и накопительную котировку, не сбрасывает статус полноты и
снова обрабатывает дальнейшие ручные реплики моделью. Отдельная кнопка
продолжения не требуется. Это не включает автоматические дозапросы для
завершённых реальных переписок.

На вкладке «Отобранные компании» добавьте получателей и канал, затем откройте
«Общение». Там показаны точный английский текст первого RFQ и список адресатов.
Кнопка отправки находится в блоке «Поставщики» и перед действием показывает
отдельное подтверждение с каналами и получателями. Если Email или
WhatsApp не включён, backend не обращается к провайдеру и сохраняет помеченную
демонстрационную коммуникацию.

Во вкладке «Сводная таблица» показывается одна актуальная строка на компанию:
повторные письма и котировки того же реального поставщика не создают дубли.
Тестовые поставщики могут повторяться: каждый тестовый диалог остаётся отдельной
строкой. В столбце
«Поставщик» выводится название компании, а в столбце «Производитель» — `Да`,
`Нет` или `Не определено` для неподтверждённой/противоречивой роли. Остальные
отдельные столбцы с горизонтальной прокруткой показывают полноту, страну закупки, фасовку, цену и единицу, предложенный объём и
MOQ, явно указанные стоимость закупки, доставка, пошлина, НДС и итог до склада,
Incoterm, документы, HAZMAT, условия оплаты, срок и минимальная уверенность
извлечённых полей. Модель не вычисляет отсутствующую денежную разбивку: такие
ячейки остаются пустыми до получения явного значения от поставщика.
Кнопка «Настроить столбцы» открывает модальное окно с независимыми наборами
галочек «На сайте» и «При скачивании таблицы». Настройки сохраняются локально в
браузере. Кнопка «Скачать CSV» экспортирует текущие строки с учётом фильтра
«Только полные» и выбранного набора столбцов; UTF-8 BOM и разделитель `;`
обеспечивают корректное открытие русского текста в Excel. Значения из
недоверенных ответов поставщиков, похожие на формулы Excel, выгружаются как
текст и не выполняются.
Первый узкий столбец на сайте не имеет текстового заголовка и содержит только
радиокнопку выбора поставщика. В разделе «На сайте» он отмечен как обязательный
и не может быть скрыт; для CSV поле «Выбор поставщика» настраивается отдельно.
Кнопка «Редактировать таблицу» переводит выбранную строку в режим редактирования
прямо в ячейках, без модального окна. Клик по изменяемой ячейке другой строки
выбирает её для следующей правки после сохранения или отмены текущей. Название
реального поставщика и значение «Производитель» обновляют реестр; коммерческие
поля, документы и HAZMAT обновляют котировку. Ручные правки сохраняются в БД и
повторно вычисляют статус полноты. Исправленные человеком поля получают
confidence `1.0`, потому что больше не зависят от автоматического извлечения;
исходная переписка при этом не изменяется. Аудитору режим редактирования недоступен.
Закупщик вручную выбирает строку. В «Итоге закупки» остаются только комментарий
и кнопка «Сохранить в историю»: карточка условий не повторяется. Каждое нажатие
создаёт отдельный снимок с автором и временем и связывает его с запросом,
веществом, поставщиком и распознанным посредником там, где эти сущности есть.
Последнее решение продолжает восстанавливать выбранную строку после входа, а
полная история доступна в реестрах веществ, поставщиков и посредников. Сохранение
ничего не отправляет поставщику. При открытии вкладки первая котировка (либо
ранее сохранённый итог) выбирается автоматически. Связанный реальный или тестовый диалог сразу
показывается под итогом на всю ширину блока; отдельной кнопки открытия или
сворачивания нет. Нажатие на имя другого поставщика либо его радиокнопку
одновременно меняет итог и показанный диалог. История показывается целиком, а
доступное по роли поле ответа позволяет продолжить эту же переписку без создания
нового диалога.

Перед генерацией любого автоматического дозапроса отдельный policy-gate
классифицирует входящее письмо. Автоответ разрешён только для стандартных тем
текущего RFQ: вещество, спецификация, цена, MOQ, документы, доставка, срок и
оплата. Личные и светские вопросы (`How are you?` / «Как ваши дела?»), вопросы не
по закупке, обязательства, опасная логистика, аналоги, кастомный синтез,
регуляторные и неясные сообщения создают эскалацию. Исходное письмо сохраняется,
но нейросеть его не отвечает; уведомление появляется у соответствующего
поставщика на вкладке «Общение». При недоступности или неоднозначном ответе
классификатора система также безопасно передаёт сообщение человеку.

## WhatsApp

В настройках доступны два транспорта: официальный `cloud_api` и неофициальный
`web`. Транспорт выбирается явно; одновременно используется только один.

### Cloud API

В разделе «Настройки» администратор указывает:

- Meta Access Token;
- Phone Number ID;
- версию Graph API.

Проверка подключения читает сведения Phone Number ID и ничего не отправляет.
Реальное текстовое сообщение отправляется только после включения канала и
отдельного подтверждения действия. Meta принимает свободный текст только в
открытом 24-часовом окне общения; для первого контакта вне окна нужен заранее
одобренный шаблон Meta. Входящий webhook Cloud API в эту реализацию не входит.

В существующем WhatsApp-диалоге поле ответа вызывает Cloud API только после
подтверждения пользователя. `wamid` сохраняется в истории; уникальный ключ
действия предотвращает повторную отправку при повторе HTTP-запроса. Если Meta не
подтвердила доставку, попытка остаётся со статусом `delivery_error` и без
автоматического повтора.

### WhatsApp Web для общения с обычного номера

Этот режим связывает обычный номер как дополнительное устройство и автоматизирует
веб-клиент через `whatsapp-web.js`. Это неофициальный API: он может перестать
работать после обновления WhatsApp и может привести к выходу из сессии или
блокировке номера. Для него следует использовать отдельный тестовый номер.

1. В production `.env` задайте случайный `WHATSAPP_WEB_SERVICE_TOKEN` длиной не
   менее 32 байт. Тот же Compose-файл передаёт его backend и gateway; через UI
   секрет не читается и не изменяется.
   Если production-сеть не открывает `web.whatsapp.com`, сохраните Xray-конфиг
   VLESS только в игнорируемом `data/xray/config.json` и задайте:
   `COMPOSE_PROFILES=whatsapp-vless`,
   `WHATSAPP_XRAY_CONFIG_PATH=./data/xray/config.json` и
   `WHATSAPP_WEB_PROXY_SERVER=socks5://xray:1080`. В этом режиме через VLESS
   идёт только браузер WhatsApp; backend, email и поиск используют обычный выход.
2. В «Настройки → WhatsApp» выберите «WhatsApp Web» и сохраните канал выключенным.
3. Рекомендуемый способ: введите номер с кодом страны, нажмите «Получить код
   привязки», затем на телефоне откройте «Связанные устройства → Привязка
   устройства → Привязать по номеру телефона» и введите восьмизначный код.
   Номер и временный код не сохраняются в БД и не попадают в логи.
4. Запасной способ — QR-код. Пока сессия не подключена, интерфейс получает
   актуальный QR каждые четыре секунды, поэтому устаревший снимок не остаётся на
   странице.
5. Дождитесь состояния `ready`, включите канал и запускайте отправку только с
   явным подтверждением.

Gateway не публикует порт на хосте, хранит сессию в Docker-томе
`whatsapp_web_data`, держит QR только в памяти и передаёт входящие сообщения
backend по внутреннему bearer-защищённому callback. Недоставленные callback-
события сохраняются в томе и повторяются. Если текущая версия Web-клиента не
возвращает штатный ID сообщения, gateway присваивает исходящему сообщению
уникальный резервный ID, а входящему — стабильный хеш-ID; это не превращает
успешную доставку в ошибку и позволяет повторно обработать уже сохранённый
callback. Gateway передаёт текст, ID процитированного сообщения и до пяти файлов;
один файл ограничен меньшим из `WHATSAPP_WEB_MAX_MEDIA_MB` и 25 МБ. Файл
сохраняется в защищённом хранилище документов и отображается у реплики во вкладке
RFQ «Общение».

Сначала входящий ответ сопоставляется с обычным RFQ-диалогом: ответ на конкретную
реплику — по провайдерскому ID, иначе — по номеру и последнему диалогу контакта.
Если с номером одновременно ведутся несколько RFQ, сообщение сохраняется в
последнем диалоге с эскалацией и не извлекает котировку до проверки человеком.
Неизвестный номер сохраняется непривязанным; отдельный раздел WhatsApp не
создаётся. Если рабочего RFQ-диалога нет, callback может быть сопоставлен с
последним реальным WhatsApp-диалогом «Тестирования общения» по keyed hash номера.
Современный внутренний WhatsApp LID отправителя сначала преобразуется
штатным методом Web-клиента в реальный номер; сам LID не используется как номер
поставщика. Стандартный рабочий ответ проходит policy-gate, сохраняет котировку и
остаётся доступным для ручного ответа из блока «Общение»; социальный, личный,
неясный или рискованный вопрос создаёт эскалацию и не получает автоответ.
При временной недоступности WhatsApp или прокси gateway сохраняет безопасный
код ошибки и повторяет инициализацию. Интерфейс показывает причину рядом с
кнопками привязки вместо молчаливого ожидания. Перед восстановлением сохранённой
сессии gateway удаляет только временные Chromium lock-файлы, которые могут
остаться после пересоздания контейнера; данные авторизации при этом сохраняются.

## Тестирование общения

Отдельный раздел расширенного тестирования виден только администратору. В рабочей
вкладке «Запросы → Общение» закупщику и администратору доступны тестовые диалоги
только по текущему доступному RFQ. Закупщик не получает произвольную
административную песочницу и режим «нейросеть — поставщик».

В рабочей вкладке «Запросы → Общение»
каждый сохранённый тестовый диалог находится в общем списке непосредственно
рядом с реальными поставщиками. Кнопка «Начать новый тестовый диалог» всегда
расположена в верхней панели над списком уже начатых диалогов, а выбор
существующего открывает его полную сохранённую историю в правой панели.
Загрузка реальной переписки и тестовых диалогов выполняется независимо:
временная сетевая ошибка тестового API не скрывает уже отправленные RFQ и
сохранённые сообщения поставщиков. Безопасные GET-запросы этого экрана один раз
повторяются при обрыве соединения; внешние отправки автоматически не повторяются.
Встроенная версия не показывает настройки канала, получателя и режима: первым
сообщением служит сохранённый RFQ текущего запроса, а пользователь отвечает на него вручную от лица
поставщика либо выбирает быстрый пример полного, неполного или нестандартного
ответа. Нестандартный пример проверяет, что policy-gate останавливает нейросеть
и создаёт эскалацию человеку. Симуляция работает в режиме `preview`, не
обращается к Email/WhatsApp и показывает, какие условия
распознаны и чего не хватает. После каждого ответа она создаёт или обновляет одну
накопительную котировку «Тестовый поставщик» у текущего RFQ; цена и остальные
распознанные условия сразу доступны в его сводной таблице. Статус «Данные
собраны» ставится только при наличии цены и валюты, Incoterm, MOQ, грейда,
условий оплаты, срока и CoA либо TDS. Все тестовые диалоги
сохраняются в PostgreSQL и привязаны к RFQ. При повторном открытии вкладки
их можно выбрать рядом с основными диалогами и продолжить с сохранённой историей.
Если policy-gate остановил тестовую переписку, пользователь вводит ручной ответ
поставщику прямо в карточке эскалации. Этот ответ сохраняется как реплика
сотрудника, не вызывает LLM и возвращает диалог в активное состояние; после него
следующий ответ тестового поставщика снова обрабатывается обычным безопасным
контуром. Кнопки примеров
становятся доступны после запуска диалога и отправляют готовый ответ на показанный
RFQ. Кнопка «Ответ с паспортом (PDF)» доступна только в preview-диалоге,
создаёт синтетический CoA под вещество и CAS текущего RFQ и не отправляет данные
во внешний канал. PDF сохраняется в обычное хранилище документов, проходит
извлечение текста и независимую LLM-проверку с детерминированной сверкой CAS и
дословных цитат. Под репликой сразу видны файл, результат проверки и раскрываемый
список понятых фактов; файл также появляется в документах RFQ. Если LLM
недоступна, файл и извлечённый текст сохраняются, но результат честно помечается
для ручной проверки. В самом PDF крупно указано, что это синтетическая
демонстрация и документ нельзя использовать в реальной закупке. Основное окно
«Предпросмотр RFQ» над панелью диалогов сворачивается и по умолчанию
закрыто. После раскрытия английский оригинал можно перевести на русский отдельной
кнопкой через Google Translate (`en -> ru`), без участия LLM; текст RFQ при этом
передаётся во внешний сервис Google и заменяет английский текст в том же блоке;
кнопка «Скрыть перевод RFQ» возвращает оригинал. Перевод не создаёт диалог, не меняет
сохранённый RFQ и не отправляется поставщику. В тестовом диалоге отдельный
повторный предпросмотр не показывается: он сразу использует сохранённый RFQ как
первое сообщение. В тестовых диалогах одна кнопка «Перевести диалог» переводит
через Google Translate все реплики сразу и заменяет оригиналы переводами в тех
же сообщениях; кнопка «Скрыть перевод диалога» возвращает оригиналы.
Такое же переключение доступно в реальных диалогах с поставщиками по Email и
WhatsApp. Перевод используется только для внутреннего просмотра, не сохраняется
вместо оригинала и не отправляется поставщику.
«Кто пишет от нейросети → Поставщик»
позволяет вручную писать как покупатель и получать ответ модели как поставщика;
для него API принудительно запрещает режим `send`. Администратор вводит общую информацию о потребности и
дополнительные требования. Выделенная облачная LLM первой формирует английское
сообщение поставщику. Затем
администратор отвечает от лица поставщика, а модель продолжает диалог с учётом
всей сохранённой истории и без коммерческих обязательств. Перед продолжением
симуляции тот же policy-gate, что и в реальных каналах, классифицирует ответ.
Личный, посторонний, опасный, регуляторный ответ, запрос обязательства, аналог,
кастомный синтез или prompt injection сохраняется, но не получает ответа модели:
диалог получает статус `escalated` и причину для человека. Реплики поставщика
передаются модели как недоверенный ввод и не могут менять системные правила.
Backend проверяет, что исходящая реплика написана на английском; при несовпадении
он один раз просит модель пересоздать сообщение, а повторно неверный результат
не отправляет. Оригиналы входящих и исходящих сообщений сохраняются без
изменений. Русский перевод создаётся только после нажатия «Перевести на русский»
у конкретной реплики, сохраняется отдельно, отображается только сотруднику и
никогда не передаётся поставщику. Повторное раскрытие использует сохранённый
перевод без нового вызова модели. Ошибка перевода не блокирует внешнюю переписку.
Активный системный промпт `supplier_communication` выбирается из раздела
«ИИ-промпты»; встроенные правила и методика описаны в
[`docs/SUPPLIER_COMMUNICATION_PROMPTS.md`](SUPPLIER_COMMUNICATION_PROMPTS.md).

Режим по умолчанию — `preview`: сообщения остаются в приложении. Режим `send`
требует полного адреса и отдельного подтверждения перед каждой исходящей
репликой. В журнале отдельно сохраняются контекст и
оригинальный текст каждой реплики, маскированный получатель, статус доставки и технический
идентификатор провайдера. Пароли и токены в журнал не записываются; для реального
WhatsApp-диалога полный номер хранится отдельно в зашифрованном виде, а поиск
входящего диалога выполняется по keyed hash.

Генератор не вводит образец, пилотную партию, контейнер или альтернативное
количество, если такого объёма нет в контексте или ответе поставщика. Перед
показом backend удаляет Markdown, строку темы, тестовые пометки, вымышленную
подпись отдела закупок и пустые финальные любезности.

Если в исходном контексте указан CAS, до генерации первого сообщения backend
проверяет контрольную сумму и запрашивает подтверждённое наименование и синонимы
в PubChem. Отдельный structured-output gate сопоставляет их с введённым названием.
Неверная контрольная сумма, явный конфликт названия и CAS либо недоступность
проверки переводят симуляцию в `escalated`; поставщику сообщение не формируется.

После генерации backend отдельно проверяет типовые смысловые ошибки: первый RFQ
из краткого контекста обязан запросить идентичность, нельзя вводить новый образец
или контейнер, спрашивать у поставщика отсутствующий destination покупателя и
повторно запрашивать уже подтверждённую форму. Нарушивший правило черновик один
раз пересоздаётся с точной причиной. Повторное нарушение останавливает отправку
со статусом `llm_error`.
