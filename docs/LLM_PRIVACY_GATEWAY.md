# Локальный шлюз конфиденциальности для облачной LLM

## Статус решения

Это утверждённая целевая архитектура ChemSource AI. На 29.08.2026 она ещё не
реализована: текущий production обращается к Yandex AI Studio напрямую через
OpenAI-совместимый API. До реализации и приёмки шлюза нельзя утверждать, что
перед облачным вызовом приложение автоматически удаляет всю чувствительную
информацию.

Точная модель семейства Qwen 8B, квантование и требования к оборудованию должны
быть выбраны по результатам измерений качества и производительности. Название
«Qwen-8B» ниже обозначает класс локальной модели, а не уже утверждённый
checkpoint.

## Цель

Облачная модель нужна для сложного планирования, извлечения, квалификации и
диалога, но не должна получать персональные данные, секреты и внутренние
коммерческие сведения заказчика, которые не нужны для конкретной операции.

Перед каждым облачным LLM-вызовом локальный шлюз в контуре заказчика должен:

1. классифицировать данные по политике конкретного сценария;
2. удалить либо заменить чувствительные значения устойчивыми псевдонимами;
3. сохранить необходимые химические и технические факты;
4. детерминированно проверить очищенный запрос;
5. либо разрешить облачный вызов, либо заблокировать его и передать задачу
   человеку.

## Поток данных

```text
Оригинальные данные в контуре заказчика
  -> детерминированное обнаружение секретов и известных идентификаторов
  -> локальная Qwen-8B: контекстная классификация и редактирование
  -> детерминированный privacy validator
  -> policy-gate
       -> allow: очищенный запрос -> облачная LLM
       -> block: без облачного вызова -> ручная проверка
  -> structured output облачной LLM
  -> обычные typed-валидаторы и safety-gates ChemSource AI
  -> при необходимости локальное восстановление псевдонимов
```

Локальная модель получает недоверенный текст как данные. Инструкции из писем,
сайтов и документов не могут изменить правила очистки или разрешить передачу
оригинала в облако.

## Что считается чувствительным

Политика должна как минимум обрабатывать:

- пароли, API-ключи, токены, cookie, строки подключения и закрытые URL;
- ФИО, личные Email, телефоны, аккаунты мессенджеров и иные персональные данные;
- название заказчика и его подразделений, если оно не требуется сценарию;
- внутренние номера заявок, договоров, счетов, партий и документов;
- историю закупочных цен, бюджеты, целевые цены и внутренние лимиты;
- закрытые списки контрагентов, клиентов и сотрудников;
- непубличные условия договоров, переписку и фрагменты документов, не нужные
  для текущего вывода.

CAS, наименование вещества, спецификация, требуемый грейд, объём, страна
поиска и публичный URL нельзя удалять автоматически только потому, что они
похожи на идентификаторы: это рабочие факты. Для каждого типа LLM-операции
нужен собственный allowlist минимально необходимого контекста.

## Формат результата локального шлюза

Локальная Qwen-8B должна возвращать strict structured output, содержащий:

- очищенный текст;
- тип, устойчивый псевдоним и расположение каждого удаления;
- перечень сохранённых обязательных фактов;
- версию политики и модели;
- оценку полноты очистки;
- причину блокировки, если безопасный результат не получен.

Например, `ООО «Заказчик»`, имя сотрудника и его Email могут стать
`<BUYER_ORG_001>`, `<PERSON_001>` и `<EMAIL_001>`. Таблица соответствия хранится
только в контуре заказчика, шифруется и не попадает в облачный prompt, логи или
ошибки провайдера. Псевдонимы должны оставаться стабильными в пределах одного
RFQ или диалога, чтобы облачная модель понимала связь реплик.

## Правило fail-closed

Облачный вызов запрещён, если:

- локальная Qwen-8B недоступна, вернула malformed output или превысила лимит;
- детерминированный validator обнаружил секрет либо запрещённый тип данных;
- обязательный химический или коммерческий факт потерян при очистке;
- уверенность очистки ниже утверждённого порога;
- политика для данного типа операции отсутствует либо имеет неизвестную версию.

В этих случаях исходные данные сохраняются только по действующим правилам
внутреннего аудита, а пользователь получает понятную причину и возможность
ручной подготовки очищенного запроса. Прямой fallback из оригинального текста
в облако запрещён.

## Аудит без утечки

Для каждого решения шлюза внутри контура сохраняются:

- correlation ID, тип операции и время;
- версии модели, промпта, политики и валидатора;
- хеш оригинального входа, но не оригинал в техническом логе;
- очищенный запрос либо его защищённая ссылка во внутреннем хранилище;
- количество удалений по типам, решение `allow`/`block` и причина;
- идентификатор последующего облачного вызова без API-ключа.

Телеметрия, исключения и трассировка, доступные вне контура заказчика, не должны
содержать оригинальный или восстановленный чувствительный текст.

## Область применения

Шлюз обязателен для всех профилей, которые отправляют данные внешней LLM,
включая основной `LLM_*`-контур и выделенный `COMMUNICATION_TEST_LLM_*`-контур.
Он применяется к поисковому планированию, квалификации поставщиков, извлечению
котировок, проверке документов и генерации сообщений.

Шлюз не заменяет политики отдельных внешних коннекторов. Web-поиск, PubChem,
Google Translate, Email и WhatsApp имеют собственные правила передачи данных и
не считаются защищёнными только из-за наличия LLM-шлюза.

## Приёмка

Перед включением шлюза в production необходимо подтвердить:

1. `sensitive_data_escape_rate = 0` на версионированном наборе известных
   секретов, персональных и коммерческих данных;
2. 100% блокировку cloud-вызова при недоступной модели, malformed output,
   неизвестной политике и срабатывании детерминированного validator;
3. 100% облачных вызовов имеют локальную audit-запись `allow`;
4. сохранение CAS, вещества, спецификации, грейда, объёма и других обязательных
   фактов измеряется отдельно для каждого сценария;
5. качество конечного structured output сравнивается с текущим облачным
   baseline на одинаковых синтетических и обезличенных примерах;
6. в логах, трассах и ошибках отсутствуют оригинальные секреты и персональные
   данные.

Один успешный пример не является приёмкой. Набор должен включать русский,
английский и китайский текст, таблицы, письма с цитируемой историей, документы,
prompt injection, неоднозначные имена и значения, похожие на CAS или артикулы.

## Этапы внедрения

1. Утвердить таксономию чувствительных данных и allowlist по операциям.
2. Выбрать Qwen-8B, квантование и минимальное оборудование через offline eval.
3. Реализовать отдельный локальный сервис с OpenAI-совместимым или внутренним
   typed-контрактом, health-check и ограниченными ресурсами.
4. Добавить детерминированные detectors, privacy validator и fail-closed gate.
5. Встроить шлюз перед единым облачным LLM-клиентом, не дублируя логику в
   отдельных бизнес-сервисах.
6. Добавить audit, UI-причины блокировки и ручную безопасную эскалацию.
7. Выполнить offline-, интеграционные, нагрузочные и security-тесты.
8. Включать production поэтапно: shadow без облачной отправки, затем ограниченный
   набор сценариев и только после этого все внешние LLM-вызовы.
