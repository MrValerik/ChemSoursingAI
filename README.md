# ChemSource AI

**ИИ-ассистент закупок химического сырья** — on-premise система для автоматизации сбора ценовых предложений и квалификации поставщиков.

Направление: агро и биотех · Итоговый продукт: on-premise ИИ-ассистент с веб-интерфейсом

---

## О проекте

Закупка химического сырья сегодня — трудоёмкий ручной процесс: специалист регистрирует запросы, ищет поставщиков и производителей, ведёт переписку с десятками контактов (преимущественно китайских) и вручную сводит ответы воедино. Ответы приходят в произвольном формате и часто без ключевых данных — цены, базиса поставки, спецификации (TDS) или сертификата анализа (CoA).

**ChemSource AI** принимает базовые параметры продукта (CAS-номер, наименование, чистота, применение, ценовой ориентир) и далее:

- проверяет вещество по CAS-номеру (PubChem);
- формирует стандартизированные RFQ под базисы CIP Moscow / FCA Shanghai / EXW;
- ведёт первичную переписку с поставщиками по email и WhatsApp;
- извлекает структурированные данные из ответов;
- сводит всё в сопоставимую таблицу для финального решения специалиста.
- позволяет управлять версионируемыми ИИ-промптами и задавать инструкции для RFQ;
- формирует через Qwen поисковый запрос, ищет кандидатов в открытой web-выдаче и
  сохраняет источник каждого результата.

Ядро системы и локальная LLM разворачиваются в контуре заказчика. Передача
поисковых запросов, сообщений или документов во внешние сервисы разрешается
только через явно включённые и согласованные коннекторы.

## Ключевые возможности

1. Приём входных данных (CAS, наименование, чистота, применение, история цен)
2. Верификация вещества по CAS и генерация RFQ (CIP/FCA/EXW)
3. Поиск поставщиков в открытых источниках
4. Авто-рассылка RFQ (Email / WhatsApp) с запросом цены, CoA, TDS
5. Извлечение данных из ответов и авто-дозапрос при неполноте
6. Сводная сравнительная таблица по поставщикам с экспортом (CSV/Excel)
7. Контроль полноты ключевых параметров
8. История коммуникаций (карточка менеджера)
9. Эскалация нестандартных кейсов на специалиста
10. Шаблоны ответов и ведение статусов запросов

Во вкладке «Запросы → Общение» перед первым контактом показываются выбранные
поставщики и точный текст RFQ. Отправка становится доступна после явной отметки
о проверке текста, каналов и адресатов. Ниже диалоги сгруппированы по
поставщикам. Нестандартное
входящее сообщение останавливает автоматический ответ и создаёт связанное
уведомление сотруднику вместе с исходной репликой. Из открытого диалога сотрудник
может после явного подтверждения реально отправить ответ через подключённый SMTP
или WhatsApp Cloud API; каждая попытка сохраняется до сетевого вызова и защищена
от повторной отправки.

Встроенная в эту вкладку администраторская симуляция использует параметры
текущего запроса и позволяет проверить многоходовый диалог без внешней отправки.
Реально отправленный Email через API тестирования может
продолжаться автоматически: отдельный IMAP-worker принимает ответ в той же
цепочке, пропускает его через безопасную классификацию и отправляет ответ
выделенной облачной модели. Нестандартная реплика останавливает нейросеть и
переводит тестовый диалог в эскалацию человеку; повторная обработка одного
`Message-ID` не выполняется.

## Архитектура

On-premise развёртывание (Docker Compose / Kubernetes). Блочная масштабируемая архитектура из семи логических слоёв со слабой связанностью и явными контрактами между модулями:

| Слой | Назначение |
| --- | --- |
| L1. Представление | SPA веб-интерфейс, BFF / API Gateway |
| L2. Прикладные сервисы | RFQ, Поставщики, Котировки, Коммуникации, Эскалации, Шаблоны, Auth/RBAC |
| L3. Оркестрация | Оркестратор ИИ-конвейера (workflow-движок) |
| L4. ИИ/ML | LLM-инференс, извлечение, OCR, перевод, эмбеддинги, Retrieval/RAG |
| L5. Интеграции | Коннекторы: Email, WhatsApp, Echemi, веб-сорсинг |
| L6. Асинхронность | Брокер сообщений, очереди, пул воркеров |
| L7. Данные и наблюдаемость | PostgreSQL + pgvector, объектное хранилище, кэш, логи/метрики/трейсы, Eval |

### ИИ-конвейер обработки запроса

`Верификация (CAS / PubChem)` → `Генерация RFQ` → `Сорсинг` → `Рассылка` → `Извлечение (structured output)` → `Контроль полноты + авто-дозапрос` → `Сводка и эскалация`

## Технологический стек

| Компонент | Технология |
| --- | --- |
| Frontend | React + TypeScript, Vite |
| Backend | Python 3.12+ / FastAPI |
| ИИ / парсинг (MVP) | Qwen3.5-27B (Q4_K_M, GGUF) через llama.cpp на Tesla T4 16 ГБ с распределением слоёв между GPU и RAM; OCR — PaddleOCR/Tesseract на CPU; эмбеддинги bge-m3 на CPU |
| ИИ / парсинг (прод) | Qwen3-32B / 30B-A3B + Qwen2.5-VL через vLLM |
| База данных | PostgreSQL + pgvector |
| Очередь / воркеры | Redis / RabbitMQ + Celery |
| Email | IMAP/SMTP-коннектор (полностью в контуре) |
| WhatsApp | Cloud API или изолированный WhatsApp Web gateway для ограниченного тестирования |
| Инфраструктура | Docker Compose / Kubernetes, GPU-узел для LLM |

Локальная LLM работает на той же ВМ как отдельная systemd-служба `qwen.service`, а Docker-контейнер backend обращается к ней по OpenAI-совместимому HTTP API. Стороннего сервиса (Ollama и т.п.) ставить не нужно. Смена модели при масштабировании — изменение конфигурации, а не кода.

## Подход к качеству извлечения

Гибрид правил и LLM с человеком в петле (HITL):

- **structured output** — LLM с жёсткой JSON-схемой котировки (function calling), а не свободный текст;
- **детерминированные валидаторы** — CAS по контрольной сумме, цены/валюты/единицы по regex и справочникам, Incoterms по словарю;
- **раздельный аудит этапов** — сырой ответ LLM, typed parsing, валидаторы и
  policy decision сохраняются независимо;
- **изолированный validator replay** — сохранённый ответ аудитора повторно
  проходит текущий typed-контракт и veto gate в новом связанном запуске без
  сети, LLM и изменения исходной трассы;
- **оценка уверенности по каждому полю** — поля с низким confidence уходят на ручную проверку или авто-дозапрос;
- **golden-датасет** — 100–300 размеченных реальных писем для измерения точности (precision/recall);
- **RAG по истории закупок** — ценовые ориентиры подтягиваются из pgvector.

## Управление ИИ и поиск поставщиков

Раздел «ИИ-промпты» содержит отдельные инструкции для извлечения котировок,
генерации RFQ, поиска, квалификации и дозапросов. Руководитель и администратор
могут создавать и изменять промпты; каждая правка создаёт неизменяемую версию.
Закупщик выбирает активный промпт и добавляет инструкции для конкретного RFQ.
Обязательная JSON-схема, проверка фактов и защита от prompt injection остаются
в backend и не редактируются через интерфейс.

В пользовательском интерфейсе внутренний термин RFQ не используется как
отдельный шаг. Пользователь создаёт закупочный запрос, выбирает одну или
несколько стран и нажимает «Создать запрос и начать поиск». Backend сохраняет
параметры и инструкции, создаёт по одной фоновой задаче поиска на страну и
возвращает карточку запроса. Вкладка «Общение» объединяет выбранных получателей,
предпросмотр и подтверждаемую отправку первого RFQ, уже начатые диалоги и
уведомления об эскалациях, требующих решения сотрудника.

Пользовательский ввод, системные промпты и ответы Qwen по умолчанию русские.
Для внешнего поиска приложение самостоятельно преобразует русское описание в
английские и китайские поисковые запросы с сохранением CAS. При обновлении
системы русифицируются только стартовые промпты с автором «система»; версии,
изменённые руководителем или администратором, никогда не перезаписываются.

Верхнеуровневый раздел «Поставщики» является единым реестром компаний. В нём
можно искать по компании, веществу, CAS и источнику, фильтровать по стране, типу,
статусу квалификации, каналам, документам и проверяемому баллу, а также переходить
к связанным закупочным запросам. Предварительно квалифицированный результат
попадает в реестр только как кандидат; подтверждение остаётся за человеком.

В карточке закупочного запроса этап «Поиск и проверка» использует Qwen для
формирования поискового плана, после чего дополняет его детерминированными
запросами по стране и получает результаты из открытой выдачи с URL и фрагментом
источника. Запуск поиска всегда связывается с конкретным запросом; вещество и CAS
берутся из его карточки и не вводятся повторно. Для Китая используются
английские запросы, китайские термины «производитель/завод» и домены `.cn`;
результаты ранжируются по географическим признакам. Дубли одного домена удаляются.
Поиск выполняется по стратегии Echemi-first: сначала проверяются индексированные
карточки товаров и поставщиков `echemi.com`, затем региональные источники. Для
Индии дополнительно используются сайты `.in`, реестр экспортёров CHEMEXCIL,
материалы CDSCO и Pharmexcil. Поскольку публичного API поставщиков Echemi нет,
автоматический поиск сохраняет ссылку на карточку платформы, а отправка RFQ через
личный кабинет Echemi требует отдельной интеграции с доступом заказчика.

Поиск не останавливается после одной удачной выдачи: перед ранним завершением он
должен покрыть Echemi, производителя, документы и обязательные локализованные
источники выбранной страны.
Интерфейс отдельно показывает число запросов в плане Qwen, фактически выполненных
поисков, сырых страниц, кандидатов после удаления дублей и квалифицированных
компаний.

Экран поиска использует progressive disclosure: на первом уровне видны только
текущий запуск, его статус, найденные кандидаты и последовательность этапов.
Настройки нового поиска, стратегия, точные запросы,
промпты, JSON, первичные страницы и доказательства находятся в независимых
аккордеонах. Пользователь может выбрать несколько стран и целевое число
поставщиков для каждой страны. Все этапы ИИ-конвейера отображаются сразу:
завершённые — зелёные, текущий — синий, будущие — серые, ошибка — красная.
После получения кандидатов система автоматически открывает первичные страницы.
Недоступная страница исключается из квалификации и заменяется следующим
кандидатом из резервной выдачи. ИИ-агент пакетами переводит проверяемые
результаты на русский,
предварительно различает производителя
и дистрибьютора, оценивает соответствие стране, отмечает упоминания CAS, GMP,
ISO, CoA и TDS, показывает риски,
недостающие доказательства и проверяемый балл с доступной пользователю
формулой. Исходный фрагмент выдачи, проверенные цитаты и URL сохраняются для
аудита. Перед включением в короткий список результат отдельно проверяет
независимый агент-аудитор. Он получает первичную страницу и уже
детерминированно проверенные утверждения, но не итоговые метки первого агента,
и может только подтвердить предварительный результат, отклонить его или
отправить на ручную проверку. Без подтверждённых доказательств точного вещества
и роли производителя кандидат в короткий список не попадает. Аудитор не
объявляет компанию надёжной и не принимает закупочное решение.
Результат автоматически попадает в реестр только как кандидат:
окончательная
квалификация выполняется по первичным документам и официальным источникам.

### Email-контур

Приложение поддерживает два режима отправки RFQ:

- `EMAIL_DELIVERY_MODE=demo` — безопасная демонстрация без внешних писем;
- `EMAIL_DELIVERY_MODE=live` — реальная SMTP-отправка после заполнения
  `EMAIL_FROM`, `SMTP_*` и `IMAP_*`.

Тема исходящего письма получает метку `[RFQ-<id>]`, а `Message-ID` сохраняется
в истории. Ручная IMAP-синхронизация доступна руководителю и администратору:
ответ связывается с RFQ, сохраняется в переписке, передаётся в конвейер
извлечения и создаёт котировку. Для неполного ответа режим
`AUTO_FOLLOWUP_MODE=draft` создаёт английский дозапрос-черновик. Значение
`send` разрешает автоматическую отправку только при одновременно включённом
`EMAIL_DELIVERY_MODE=live`; `off` полностью отключает дозапросы.

Вложения пока сохраняются как безопасные метаданные (имя, MIME-тип и размер);
OCR и долговременное хранилище файлов остаются отдельным этапом. Администратор
может сохранить зашифрованные SMTP/IMAP и WhatsApp Cloud API настройки через
интерфейс, либо связать отдельный тестовый номер через WhatsApp Web по
восьмизначному коду или автоматически обновляемому QR, проверить
соединения и использовать отдельную вкладку симуляции общения с LLM. В Web-
режиме входящие ответы тестового диалога классифицируются и продолжаются
автоматически; нестандартные сообщения эскалируются человеку.
Если `web.whatsapp.com` недоступен из production-сети, только изолированный
WhatsApp-контейнер можно направить через Xray/VLESS; секретный конфиг остаётся в
игнорируемом `data/xray/config.json` на сервере и не попадает в Git.

## Безопасность и приватность

Решение работает в контуре заказчика: ролевой доступ (RBAC), журнал действий, шифрование вложений (CoA/TDS) и контролируемый исходящий шлюз с белым списком доменов.

> **Примечание по WhatsApp.** Cloud API — официальный вариант Meta, при котором
> сообщения проходят через инфраструктуру Meta. Дополнительно реализован
> неофициальный WhatsApp Web gateway для ограниченного тестирования обычного
> номера; он может нарушать правила WhatsApp, нестабилен и создаёт риск блокировки
> аккаунта. Email-канал (IMAP/SMTP) предпочтителен для конфиденциальных условий.

## Этапы реализации

Итерации по 2 недели, команда 4–5 человек. Ориентировочно до пилота — **12–16 недель**.

0. Подготовка — доступы, baseline-метрики, развёртывание Qwen3-8B
1. MVP-прототип — веб-интерфейс, имитация конвейера
2. Ядро + БД — backend, модель данных, генерация RFQ, сводная таблица
3. ИИ-парсинг — локальная LLM, OCR, извлечение, golden-датасет
4. Интеграции — Email, WhatsApp Cloud API, веб-сорсинг, PubChem
5. Эскалация и история — карточки менеджеров, шаблоны, статусы
6. Пилот и приёмка — on-premise развёртывание, обучение, доработки
